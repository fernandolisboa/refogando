# ADR-0010 — Stack e decisões conscientes (reversíveis, registradas para contexto)

Status: aceito

Decisões de tecnologia que **não** são ADRs "duros" (são reversíveis ou convencionais), mas cuja razão é load-bearing e merece ficar escrita para não ser re-litigada:

- **Next.js (última estável, App Router)** — escolha convencional; usar sempre a major estável mais recente, sem pinar numa versão velha (a menção a "15" era só o estado da arte na época desta decisão). SSR + i18n + route handlers para o **streaming da IA token-a-token** (route handler, não Server Action, para o streaming de geração).
- **Drizzle ORM (sobre Prisma)** — escolhido pelo **controle SQL-first**: FTS por idioma (`tsvector` / `regconfig` / `unaccent`), `pgvector` e JSONB transparentes ficam diretos no Drizzle, enquanto o Prisma abstrai longe demais para este domínio. Baixo lock-in — o schema sobrevive a uma troca. A rejeição do Prisma é **não-óbvia**, por isso registrada.
- **Neon Postgres (banco adotado)** — vendor serverless; um único datastore (Postgres) cobre relacional + FTS + `pgvector` (extensões confirmadas no Neon — ver ADR-0008). A connection string é o ponto de acoplamento e o harness de teste é provider-neutro (qualquer Postgres serve; Testcontainers `pgvector/pgvector:pg17` no CI), então trocar de vendor continua viável.
- **Vercel (hospedagem/deploy, adotada)** — domínio `refogando.com` comprado na Vercel e o app hospedado lá; SSR, i18n e os route handlers de streaming do Next.js encaixam direto. A integração **Vercel-Managed Neon** cria uma preview branch de banco por PR (naming `preview/<git-branch>`), removida ao fechar/mergear o PR pela GitHub Action `.github/workflows/cleanup-neon-preview-branch.yml` (issue #29). Escolha consciente por preferência e por já estar integrada — não por travar requisito de produto. Reversível: nada do produto depende de API proprietária da Vercel, então sair = apagar a Action + remover a integração Vercel/Neon.
- **Versões: última estável** — para toda dependência, usar a versão estável mais recente no momento da implementação, fixada por lockfile; não pinar em majors defasadas salvo conflito real. Greenfield não tem motivo pra começar atrasado.
- **Vercel Blob (storage de imagem, adotado)** — para foto de receita, imagem gerada por IA e avatar, atrás de uma **interface fina** (`storeImage`/`deleteImage`) que mantém o provedor trocável. Escolha por atrito-zero (já tudo na Vercel, sem conta externa, integra com o fluxo de preview-branch). **Plano B documentado:** Cloudinary (REST puro + otimização nativa) se a versão do `@vercel/blob` esbarrar no cutoff de npm do ambiente. Otimização de entrega via `next/image` (`remotePatterns`); redimensionar no cliente antes do upload (limite ~4,5MB de body das functions da Vercel). A **modelagem** da imagem de receita (entidade, ref-count, moderação) é decisão dura à parte: ADR-0016.

Estas são conscientes, não congelam o schema, e podem ser revistas sem o peso de um ADR próprio.
