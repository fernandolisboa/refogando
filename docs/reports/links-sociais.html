Links de redes sociais no footer — design de feature

Design de feature pronto para implementar

Resumo executivo

Recomendação clara: persistir os links sociais como um novo eixo social_links (jsonb) na linha singleton app_config — NÃO em env. O requisito do dono ("editável sem acoplar a deploy") elimina env por definição na Vercel (mudar env exige redeploy), e o repo já tem TODA a maquinaria pronta para um eixo novo de config: singleton com CHECK (src/db/schema.ts:759-806), loader com re-validação fail-safe na leitura (src/server/app-config.ts:62-108), PUT com upsert parcial por eixo (src/app/api/admin/config/route.ts:42-161), seção de UI admin clonável (src/components/admin/catalog-disclosure-config-section.tsx) e padrão de parser puro em src/domain/*-config.ts. A validação de URL segura já existe e deve ser REUSADA: safeHttpUrl em src/domain/links.ts:56-71 (allowlist http/https estrita, mata javascript:/data:/protocol-relative — proteção XSS já testada). O render entra no site-footer.tsx (client) com os links threadados do servidor pelo layout, exatamente como initialTheme (src/app/[locale]/layout.tsx:98). Shape: [{platform, url, label?, enabled}] com allowlist de plataformas EM CÓDIGO. Feature pequena (~10 arquivos, 1 migração jsonb com default []), totalmente autônoma, sem decisão irreversível.

Decisão: app_config vs env — por que app_config vence

Recomendação: app_config. Comparativo honesto:

Critérioapp_config (DB)env var
Editável sem deploy✅ PUT /api/admin/config, efeito no próximo request❌ na Vercel, mudar env exige redeploy — viola o requisito do dono
Validação✅ server-side no PUT (400 config_invalida), + re-validação fail-safe na leitura❌ zero — um typo em JSON-na-env quebra silenciosamente em produção
UI de edição✅ padrão pronto (seções admin já existem)❌ dashboard da Vercel, fora do produto
Auditoria✅ updated_at na linha (src/db/schema.ts:803)❌ nada
Estrutura✅ jsonb tipado ($type<SocialLinksConfig>)❌ string única, parse manual frágil
Custo1 SELECT que o layout já faz (ver seção de leitura — dá pra consolidar em zero queries extras)zero
Precedente✅ 7 eixos já coabitam a linha (imageGen, webSearch, catalogDisclosure, popularity, recipeVariant…)env é usada só p/ segredos (CRON_SECRET, BREVO_API_KEY)

O único argumento pró-env (custo zero de query) morre porque o layout raiz já lê app_config a cada request (src/app/[locale]/layout.tsx:74, loadRecipeVariantConfig). Env fica para SEGREDOS; config de produto editável vive no singleton — é a convenção documentada do repo (comentário em src/server/app-config.ts:33-42).

Shape e validação — novo domínio src/domain/social-links-config.ts

Módulo PURO espelhando catalog-disclosure-config.ts (mesmo contrato {ok:true,value}|{ok:false}):

export const SOCIAL_PLATFORMS = ['instagram', 'x', 'tiktok', 'youtube', 'facebook', 'pinterest', 'threads', 'bluesky'] as const
export type SocialPlatform = (typeof SOCIAL_PLATFORMS)[number]
export type SocialLink = { platform: SocialPlatform; url: string; label?: string; enabled: boolean }
export type SocialLinksConfig = SocialLink[]
export const DEFAULT_SOCIAL_LINKS_CONFIG: SocialLinksConfig = []
export const SOCIAL_LINKS_MAX = 8
export const SOCIAL_LABEL_MAX_LEN = 40
// Nome de exibição por plataforma (marca própria, NÃO se traduz — sem i18n):
export const PLATFORM_DISPLAY: Record<SocialPlatform, string> = { instagram: 'Instagram', x: 'X', ... }
export function parseSocialLinksConfig(raw: unknown): { ok: true; value: SocialLinksConfig } | { ok: false }

Regras do parse (na ordem, mesmo estilo de validateLinks em src/domain/links.ts:83-103):

  1. array (lista vazia é VÁLIDA — footer limpo);
  2. length <= SOCIAL_LINKS_MAX;
  3. cada entrada é objeto com platform na allowlist (fechada, EM CÓDIGO — mesma tese do ALLOWED_MODELS em src/app/api/admin/config/route.ts:33: allowlist muda mais rápido que migração);
  4. sem plataforma duplicada (um link por rede mantém o footer são);
  5. url validada por safeHttpUrl IMPORTADA de src/domain/links.ts:56-71 — NÃO duplicar: essa função já mata javascript:/data:/vbscript:/protocol-relative //evil.com, exige host, cap 2048, e tem teste em test/unit (é a mesma defesa XSS do perfil público);
  6. label opcional: string trimada, vazia ⇒ omitida, > SOCIAL_LABEL_MAX_LEN ⇒ rejeita;
  7. enabled boolean obrigatório — permite o dono CADASTRAR links hoje e ligar quando as contas existirem ("futuras", requisito literal).

Ordem do array = ordem de render no footer (o admin controla a ordem reordenando).

NÃO reusar LINK_TIPOS (src/domain/links.ts:15) — é a allowlist do PERFIL de usuário (github, site); a do site é outra superfície de produto com curadoria própria. Reusa-se só safeHttpUrl.

Schema + migração (drizzle 0052)

Uma coluna jsonb na MESMA linha singleton (padrão idêntico a webSearchAllowlist src/db/schema.ts:785-788 e recipeVariantConfig :778-781). Inserir após popularityConfig (src/db/schema.ts:802), antes de updatedAt:

// Links de redes sociais do SITE (footer). jsonb SocialLink[] na linha singleton — editável pelo
// admin sem deploy. Default [] (footer sem links até o admin cadastrar). Read-path re-valida
// (parseSocialLinksConfig) — linha legada/lixo cai em [] (fail-safe: nunca renderiza link inválido).
socialLinks: jsonb('social_links')
  .$type<SocialLinksConfig>()
  .notNull()
  .default(DEFAULT_SOCIAL_LINKS_CONFIG),

Gerar com npm run db:generate → drizzle/0052_*.sql. Gotchas de memória do projeto: rodar o generate NA WORKTREE da feature; grep no .sql novo por DDL fantasma (search_vector/hnsw/gin) como rede de segurança; migrate-on-deploy cuida da produção (dev==prod, único Neon).

Leitura fail-safe + threading servidor→footer

src/server/app-config.ts — 4 toques, todos com padrão na cara:

  1. campo socialLinks: SocialLinksConfig no tipo AppConfig (linha 46-60);
  2. default no branch sem linha (linha 64-74): socialLinks: DEFAULT_SOCIAL_LINKS_CONFIG;
  3. re-validação na leitura (dentro do return, linhas 82-107): parseSocialLinksConfig(row.socialLinks) — inválido ⇒ [] (mesma disciplina do popularity linha 78 e do recipeVariant linha 81: linha editada à mão NUNCA envenena o render);
  4. atalho loadSocialLinksConfig(db) espelhando loadCatalogDisclosureConfig (linhas 116-118).

src/app/[locale]/layout.tsx — o footer é client e NÃO faz fetch (comentário site-footer.tsx:4 "Sem chamadas de dados"); os dados chegam por prop, como initialTheme (layout linha 98). Carregar com o MESMO try/catch gracioso do variantEnabled (linhas 72-77): soluço do Neon ⇒ [], footer sem links, nunca tela quebrada. Filtrar enabled NO SERVIDOR antes de threadar — o client só recebe links visíveis (payload menor; link desligado não vaza no HTML).

Micro-otimização recomendada no mesmo PR: o layout hoje chama loadRecipeVariantConfig (1 SELECT) e passaria a chamar loadSocialLinksConfig (2º SELECT da MESMA linha). Trocar por UMA chamada loadAppConfig(getDb()) no try e destruturar recipeVariant.enabled + socialLinks — zero query extra vs hoje.

Render no footer (site-footer.tsx)

Nova prop socialLinks?: SocialLink[] (default []). Bloco novo logo após o div dos links legais (src/components/site-footer.tsx:30-37), renderizado SÓ quando socialLinks.length > 0 (footer limpo por default).

Dois padrões do repo a respeitar:

  • Landmark: o comentário em site-footer.tsx:28-29 decide explicitamente usar <div> (não <nav>) nos links legais "para não criar um segundo landmark de navegação além do header". Seguir a mesma decisão: <div> com aria-label nos anchors individuais (o requisito pede aria-label por link, não landmark).
  • Endurecimento de link externo: copiar de src/components/profile/public-profile-view.tsx:107-119 — target="_blank" + rel="noopener noreferrer" (sem nofollow: são as redes PRÓPRIAS do site, o repo usa nofollow só em conteúdo de terceiro, cf. recipe-detail-view.tsx:339).
{socialLinks.length > 0 && (
  <div className="mt-1 flex flex-wrap gap-x-4 gap-y-1 text-sm text-muted">
    {socialLinks.map((l) => (
      <a key={l.platform} href={l.url} target="_blank" rel="noopener noreferrer"
         aria-label={(l.label ?? PLATFORM_DISPLAY[l.platform]) + ' — ' + messages.footer.abreEmNovaAba}
         className="hover:text-fg hover:underline">
        {l.label ?? PLATFORM_DISPLAY[l.platform]}
      </a>
    ))}
  </div>
)}

Texto visível = label ?? PLATFORM_DISPLAY[platform] (nomes de marca não se traduzem; só o sufixo do aria-label "abre em nova aba" é i18n). REGRA DE MEMÓRIA do dono: nenhuma copy nova pode rotular o app como "bilíngue" nem enumerar idiomas.

Recomendações

P2

Implementar social_links como novo eixo do app_config (domínio + migração + loader + PUT + footer + admin UI + testes)

Delegável ao agenteesforço: pequeno

Requisito do dono (editável sem deploy) + toda a maquinaria já existe (singleton, upsert parcial por eixo, parser puro, seção admin clonável, safeHttpUrl testada). Feature de baixo risco: default [] mantém o footer exatamente como hoje até o admin cadastrar; flag enabled por link permite cadastrar contas futuras e ligar depois.

P2

Reusar safeHttpUrl de src/domain/links.ts:56 — não duplicar validação de URL

Delegável ao agenteesforço: trivial

A função já implementa a allowlist http/https estrita que mata javascript:/data:/protocol-relative (XSS armazenado em link clicável) e já tem cobertura de teste. Duplicar criaria uma segunda fonte de verdade de segurança que pode divergir.

P2

Consolidar o layout raiz em UMA chamada loadAppConfig (recipeVariant + socialLinks)

Delegável ao agenteesforço: trivial

src/app/[locale]/layout.tsx:74 já faz 1 SELECT em app_config por request; adicionar loadSocialLinksConfig ingenuamente dobraria para 2 SELECTs da mesma linha em TODA página. Destruturar os dois eixos de uma única loadAppConfig mantém o custo em zero queries extras.

P3

Escolher a lista final de plataformas da allowlist com o dono

Precisa de vocêesforço: trivial

A allowlist proposta (instagram, x, tiktok, youtube, facebook, pinterest, threads, bluesky) é palpite razoável para app de receitas pt-BR, mas quais redes o Refogando terá é decisão de produto/marketing do dono. Reversível e barata (allowlist em código, sem migração) — dá para shipar com a proposta e ajustar depois; só não vale travar a implementação nisso.

Por que precisa de você: Decisão de presença de marca (quais redes sociais o dono pretende abrir) — não inferível do código.

P3

Criar seção /admin/site (Governança) em vez de enfiar a config numa aba existente

Delegável ao agenteesforço: trivial

Links do site são chrome/identidade, não Curadoria nem IA nem Descoberta. Uma aba 'Site' admin-only custa ~2 arquivos (page clonada + item no section-nav.tsx:31-38) e vira o lar natural de futuras configs de chrome (o catalogDisclosure poderia até migrar para lá um dia).
