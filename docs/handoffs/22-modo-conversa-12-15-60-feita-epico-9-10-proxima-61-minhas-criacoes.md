## Como o Modo conversa funciona (mapa pro #61 e pra manutenção — código é a fonte de verdade)

- **Duas chamadas distintas ao Claude (ADR-0009):** (1) `streamConversation` STREAMA texto conversacional token-a-token; (2) a **destilação** é a chamada CONSTRITA existente (`generateRecipe` → `RecipeGenSchema` → `classify` → `persistGeneration`), alimentada por `buildConversationPrompt(transcript)`. A saída estruturada NÃO mudou; o que mudou é a ENTRADA (transcript) e o COMO (stream vs await).
- **Wire = NDJSON** (não SSE; o repo não tem EventSource): `POST /api/conversations/stream` devolve um `ReadableStream` de linhas JSON — `{type:'token',text}*` e então **exatamente um** frame terminal: `{type:'recipe',outcome,recipeId,advisory,avisos?}` | `{type:'impossible',advisory}` | `{type:'error',error:'geracao_invalida'|'conflito_concorrente'}`. O frame `recipe` espelha o 201 de `/api/generations` (devolve `recipeId`, NÃO o corpo → a UI faz um **2º GET** `/api/recipes/{id}?locale=`). **Assimetria de transporte (documentada na rota, não "consertar"):** INVALID na destilação roda DEPOIS do stream abrir → não pode usar status HTTP (headers já enviados) → é SEMPRE o frame in-band `{type:'error'}`.
- **Ciclo de vida da sessão (a tensão #12↔#15, resolvida):** #12 é in-flight/stateless (o cliente segura o transcript e reenvia inteiro a cada turno); #15 moveu a criação da sessão pro COMEÇO (`POST /api/creation-sessions`) e a rota de stream agora HONRA `sessionId` (reusa só se existe E é do dono, senão lazy-create — fail-closed, nunca escreve na sessão alheia). Cada turno persiste só a CAUDA nova (último user + assistant acumulado, 2 linhas, `seq = coalesce(max(seq),-1)+1`, bump `updated_at`, tudo numa tx; só se NÃO abortado).
- **Apagar transcript ≠ apagar Receita:** `DELETE .../transcript` faz hard-delete das linhas + zera `generation.advisory_comment` de TODAS as gerações da sessão (escopo de sessão — pode haver várias), mas a Receita + `result_kind` ficam. Irreversível (confirmação é da UI #60).
- **`persistGeneration` se autodefende:** `assertOwnedSession` no topo do ramo `existingSessionId` + `eq(userId, ownerId)` nos dois UPDATEs (ESTOURA fail-closed se sessão não-própria) — defesa em profundidade além da posse provada na rota.
- **Auth FAIL-CLOSED** (`requireSession`): conversa exige Usuário logado (`creation_session.user_id NOT NULL`). **Anônimo-efêmero é #22, fora de escopo** — relaxar `user_id` é a fronteira do #22 (relevante pro #61).
